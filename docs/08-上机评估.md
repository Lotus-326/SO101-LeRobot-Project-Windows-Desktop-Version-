# 08 · 上机评估（策略驱动真机）

> ⚠️ 这一步机械臂会**自己动**。务必清空工作空间、固定好机械臂、
> 手放在能立刻断电的位置，全程有人看守。

---

## 1. 原理

LeRobot 0.4.x 的真机评估不是 `lerobot-eval`（那个是给 Libero/MetaWorld 等
仿真环境用的），而是：

> **`lerobot-record` + `--policy.path=<权重>`**

加了 `policy` 之后就不再需要 Leader 遥操作，动作由策略输出，
同时把整个过程录成一个 `eval_` 开头的新数据集，方便回看复盘。

---

## 2. 运行评估

```powershell
powershell -ExecutionPolicy Bypass -File scripts\10-eval.ps1 `
  -PolicyPath outputs/train/act_m1_pick_cube/checkpoints/last/pretrained_model
```

常用参数：

```powershell
-NumEpisodes 10      # 评估回合数
-EpisodeTimeS 50     # 每回合时长
-RepoId seeedstudio123/eval_act_m1_v1
-NoDisplay           # 不弹预览窗（省 CPU）
```

也可以直接用 Hub 上的模型仓库名：

```powershell
powershell -ExecutionPolicy Bypass -File scripts\10-eval.ps1 -PolicyPath <HF_USER>/act_m1_pick_cube
```

---

## 3. 必须满足的前提

| 前提 | 说明 |
| --- | --- |
| 机器人 ID 一致 | `--robot.id` 必须与采集数据时相同（校准文件） |
| **相机键名一致** | `front` / `side` / `orbbec_color` 必须与采集时**完全一致** |
| 相机位置一致 | 评估时的相机位置/角度/光照应尽量还原采集时 |
| 场景一致 | 桌面高度、物体、背景尽量一致，否则泛化不了 |

---

## 4. 结果解读

评估数据集里能直接看到：

- 每个 episode 的视频（策略是否真的完成任务）
- 成功/失败次数（人工看视频统计即可）

成功率低的常见原因：

| 现象 | 原因 | 对策 |
| --- | --- | --- |
| 完全不动 / 动作幅度极小 | 训练步数不够 | 继续训练 |
| 前几次对、后面漂移 | 数据里位置变化太少 | 补采不同位置的数据 |
| 抓空 / 撞台面 | 相机位置与采集时不同 | 还原相机位置 |
| 接近物体但抓不住 | 夹爪动作样本少 | 补采抓取瞬间的数据 |
| `mean is infinity` | 相机键名不一致 | 核对 `Cameras` |

---

## 5. 评估阶段常见报错

| 报错 | 处理 |
| --- | --- |
| `File exists: '...\seeed\eval_xxxx'` | 删掉这个 `eval_` 开头的目录再跑 |
| `mean is infinity ...` | 相机键名/顺序与采集时不一致 |
| 策略输出动作但机械臂不动 | 检查 Follower 是否上电、串口是否被占用、`--robot.id` 是否正确 |
| 动作方向完全相反 | 校准文件不对，重新校准 |

## 6. 异步推理（进阶）

数据量大 / 模型大导致推理跟不上 30Hz 时，LeRobot 支持
**异步推理**：策略服务端只负责生成 action chunk，客户端按 fps 消费。

关键参数：

| 参数 | 含义 | 典型值 |
| --- | --- | --- |
| `actions_per_chunk` | 一次推理输出多少动作 | 10 ~ 50 |
| `chunk_size_threshold` | 队列剩余比例 ≤ 该值时请求新块 | 0.5 ~ 0.7 |
| `fps` | 客户端执行频率 | 30 |

判断标准：队列**经常空** → 加大 `actions_per_chunk` / `chunk_size_threshold`，
或降低 `fps`。用 `--debug_visualize_queue_size=true` 可以画队列曲线。
